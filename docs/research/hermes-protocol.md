## 0. Resumen de arquitectura (verificado en código)

Hermes no tiene UN gateway: tiene tres superficies servidor que conviene no confundir (doc `desktop.md` §"The remote backend is a running `hermes serve` process" + `website/docs/user-guide/features/web-dashboard.md:170-186`):

| Superficie | Proceso | Transporte | Código |
|---|---|---|---|
| **Dashboard/backend** | `hermes serve` / `hermes dashboard` (FastAPI, puerto por defecto **9119**: `hermes_cli/web_server.py:1472`) | HTTP REST + WS `/api/ws` (JSON-RPC), `/api/pty`, `/api/display/ws`, `/api/audio/speak-stream`, `/api/pub`, `/api/events`, `/api/console` | `hermes_cli/web_server.py` + `hermes_cli/web_routers/*` + `hermes_cli/dashboard_auth/*` + `tui_gateway/ws.py` |
| **Gateway de mensajería** | `hermes gateway run` (aiohttp; plataformas Telegram/WhatsApp/Signal/…) + **API server OpenAI-compatible** embebido, puerto **8642** (`gateway/platforms/api_server.py:214 DEFAULT_PORT = 8642`) | HTTP `/v1/*`, `/api/sessions/*`, `/api/jobs/*`, SSE; WS browser-control | `gateway/platforms/api_server*.py`, `gateway/run.py` |
| **Rooms/groups driver** | Servicio interno del backend/gateway (proceso propietario) | accedido vía JSON-RPC `groups.*`; réplica vía RoomLink HTTP con grants | `gateway/hosted_rooms.py` (DB `shared-state.db`, `gateway/hosted_rooms.py:398-413`), `tui_gateway/hosted_room_service.py` |

El chat del Desktop contra un backend remoto va SIEMPRE por el dashboard (`hermes serve`), no por el gateway de mensajería. El app es un cliente JSON-RPC sobre `/api/ws` (`apps/desktop/src/api/client.ts`, clase `HermesGateway extends JsonRpcGatewayClient`).

**Contrato generado**: `tui_gateway/contracts/registry.py` declara que Python es la única fuente de verdad; `scripts/gen_gateway_contracts.py` renderiza a TypeScript + OpenRPC en `apps/shared/src/gateway-contract.generated.ts` y `gateway-contract.openrpc.json` (verificados: existen en el repo). Cada método/evento/payload es un modelo Pydantic; `Params` es `extra="forbid"` (clave desconocida ⇒ error JSON-RPC **4000** con la ruta del campo; `registry.py::validate_params`). En total en este commit: **474 métodos**, **80 eventos+server-requests** (68 eventos, 12 server-requests, contados de las declaraciones `method(...)`/`event(...)`/`server_request(...)`).

## 1. Gateway dashboard: autenticación, transporte, rutas

### 1.1 Proveedores de sesión (login usuario/contraseña: SÍ)

- Contrato base: `hermes_cli/dashboard_auth/base.py::DashboardAuthProvider` con flags `supports_password` / `supports_session`.
- **Usuario/contraseña**: `plugins/dashboard_auth/basic/__init__.py::BasicAuthProvider` — sesión = **token HMAC firmado sin estado** (no hay tabla de sesiones), contraseñas con **scrypt** estándar (`hash_password` produce `scrypt$n$r$p$<salt>$<dk>`); login hashea siempre aunque el usuario no exista. Config: `dashboard.basic_auth.{username,password_hash|password,secret,session_ttl_seconds}` o env `HERMES_DASHBOARD_BASIC_AUTH_*`. TTL de access **12 h** por defecto, refresh **30 días** (`_DEFAULT_TTL_SECONDS`, `_REFRESH_TTL_SECONDS`); el middleware refresca transparentemente con el refresh token.
- **OAuth (Nous Portal) u OIDC self-hosted**: `plugins/dashboard_auth/nous/`, `plugins/dashboard_auth/self_hosted/`; doc `desktop.md:487` ("OAuth (Nous Portal) — preferred…Register the dashboard with `hermes dashboard register`").
- Login por formulario: `POST /auth/password-login` (`dashboard_auth/routes.py:372`, body `{provider, username, password, next}` → `{"ok":true,"next":…}`; 401 genérico, 429 rate-limit 10 intentos/60 s por IP con ventana deslizante en proceso).

### 1.2 Sesiones, cookies y renovación

- Cookies (nombres exactos, `hermes_cli/dashboard_auth/cookies.py:27-31`): `hermes_session_at` (access token), `hermes_session_rt` (refresh token), `hermes_session_provider`, `hermes_session_pkce`, `hermes_sso_attempt`. Atributos `httponly; samesite=lax` (HTTP) o `samesite=none; Secure` en HTTPS (`cookies.py:60-71`).
- Renovación: middleware transparente con el RT de 30 días; y para apps nativas `POST /auth/native/refresh` (body `{refresh_token, provider?}` → `_bearer_payload`; 401 `{"error":"session_expired"}` cuando todos los proveedores rechazan el RT — `routes.py:496-520`).
- Payload bearer nativo (`routes.py:110-114::_bearer_payload`): `{access_token, refresh_token, token_type:"Bearer", expires_at, provider, user_id}`.

### 1.3 Login nativo RFC 8252 (lo que usa el Desktop)

- `GET /auth/native/authorize` con `code_challenge` (S256 obligatorio) + `redirect_uri` **restringido a loopback** `http://127.0.0.1[:port]/…` (rechaza `localhost`, RFC 8252 §8.3) + `state` (`routes.py:242-289`, `_validate_loopback_redirect_uri`).
- Callback de escritorio: `GET /auth/native/authorize` devuelve redirect al loopback con `code`; el Desktop canjea en `POST /auth/native/token` (body `{code, code_verifier}`) → `_bearer_payload` en JSON, **sin cookies** (`routes.py:476-493`).

### 1.4 WS: tickets de un solo uso

- `POST /api/auth/ws-ticket` (requiere sesión): mintea ticket de **30 s, single-use** (`ws_tickets.py:21 TTL_SECONDS = 30`), respuesta `{"ticket", "ttl_seconds"}` — "browsers cannot set Authorization on the upgrade" (`routes.py:458-474`).
- Consumo en upgrade (`hermes_cli/web_server_chat.py:220-295::_ws_auth_reason`):
  - Modo gated (bind no-loopback): `?ticket=` o subprotocolo `hermes-gateway-ticket.<ticket>` junto con el protocolo base `hermes-gateway-v1` (`web_server_chat.py:202 _GATEWAY_WS_PROTOCOL`, `:206-217`). Un ticket de display presentado como login se rechaza.
  - Modo loopback/insecure: legado `?token=` comparado constant-time contra `_SESSION_TOKEN` (rechazado en modo gated).
  - Credencial interna de proceso para hijos PTY/TUI: `?internal=` (`consume_internal_credential`, nunca inyectada al SPA).
- Códigos de cierre documentados y en código: `4401` ticket inválido, `4403` guard Host/peer, `4400` canal ausente (`chat_ws.py:626`), doc `web-dashboard.md:222`.
- Identidad autenticada estampada en `ws._hermes_auth_identity` `{user_id, provider}` = autoridad para RPCs privilegiados (`browser.controller.register`) (`chat_ws.py:593-611`, `tui_gateway/ws.py:290-299`).

### 1.6 Transporte WS del chat: JSON-RPC

- **Frame**: JSON-RPC 2.0 delimitado por línea (newline-delimited) en ambos sentidos; primer frame servidor→cliente siempre `{"jsonrpc":"2.0","method":"event","params":{"type":"gateway.ready","payload":{"skin":…,"change_events":true,"heartbeat":true,"replay_epoch":"<uuid>"}}}` (`tui_gateway/ws.py:1-4` docstring, `:325-331`).
- **Eventos**: envelope `{"jsonrpc":"2.0","method":"event","params":{"type":<nombre>,"session_id":<sid>,"payload":{…}}}` (`tui_gateway/server.py:660-663::_event_frame`). Sin payload ⇒ sin clave `payload`. Eventos globales sin `session_id` (p.ej. `skin.changed`).
- **Heartbeat**: cliente envía `gateway.ping` (respuesta `{"result":{"ok":true}}`); el cliente pinge cada 15 s (`tui_gateway/ws.py:20-23`, manejo en `ws.py:375-379`).
- **Replay/reconnect**: cada evento lleva `seq` monótono por sesión (estampado en `event_replay.py::_stamp_event`); ring buffer de 512 eventos / 4 MiB por sesión, 64 sesiones / 64 MiB por proceso; el cliente llama `session.events.since` con `last_seen`; `replay_epoch` (uuid por proceso) detecta reinicio del backend y fuerza reset de watermark (`event_replay.py:1-48`). Respuesta: `{events[], latest_seq, truncated, count}` (contrato `sessions.py:673-681`).
- **Errores**: `-32601` método desconocido ("client and backend out of sync; run `hermes update`"), `-32700` parse, `-32603` crash, `4000` params inválidos (extra_forbidden), dominio por handler (4006 missing session_id, 4015 bad url, 4124 turn_author, 5300 viewer_mismatch, 4403 browser-controller…).
- **Capacidades**: `client.capabilities` (cliente→servidor, tras `gateway.ready`; declara `server_requests: bool`) y `gateway.capabilities` → `{per_session_exclusive_submit: bool}` (`contracts/liveness.py`). Un cliente WS que no declara `server_requests` se trata como build antiguo y **no recibe server→client requests**.

Camino remoto: `tui_gateway/hosted_room_peer_http.py::PeerRunsHTTPClient` — corre el turno del miembro con la Runs API del peer (`POST /v1/runs`), hace polling, y resuelve con `POST /v1/runs/{run_id}/approval` body `{choice, request_id}` autenticado con **room grant** (cabecera `Authorization: HermesRoom <token>` — `gateway/platforms/api_server_room_grants.py:81-84`; estado `waiting_for_approval` con `approval` en el status del run, `api_server_runs.py:857`).
- **Multi-gateway / sincronización**: réplica por páginas — `groups.replicate` (ingesta idempotente de una página `groups.log` con estampas de autoridad), `groups.replica_state`, y transferencia de autoridad por fencing: `groups.promote` (epoch+1, exige `confirm:true`), `groups.demote` (fence contra epoch probado más nuevo). Rutas peer (RoomLink): `groups.peer.invite` (grant firmado con TTL), `groups.peer.revoke`, `groups.peer.register` (registra y sondea la ruta en el room home; valida `ROOM_LINK_PROTOCOL_VERSION = 2`, `gateway/hosted_room_peer.py:30`).

Ventanas documentadas y constants: miembro working expira a 3 h si reporta trabajo, 3 min de silencio; sala observa 3 h más; máx 10 mensajes por send y 3 rondas (doc bot-mode §"Groups and group chats" — la maquinaria de tiempos vive en `gateway/hosted_room_*.py`/`tui_gateway/hosted_room_driver.py`; los literales 3h/3min/10msg/3rounds NO se localizaron como constantes nombradas en este commit: ver §9).
